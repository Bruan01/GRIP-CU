**日期**：2026-09-19（原稿 2026-09-10；已补 Qwen2.5-7B 训练、官方全量评测、数据来源核对，以及实验 H smoke）

**对接的基线代码**：RecurrentGRIP 快照 `v1_1_nell23k_first_2026-08-29/grip-exp`  
**数据 / 模型**：NELL23K 关系预测。0.5B smoke 用对齐后的关系预测划分；7B 用 `grip_nell23k_tasks.json`（论文 context + summarization + 生成 QA）训练，评测始终用官方对齐的 10-way val/test。LoRA 配方不变：MLP r=4 / α=8，作用在全部 `down_proj` / `up_proj` / `gate_proj`。

## 先看术语（后文一律用全称或固定简称）

| 说法 | 指什么 |
|---|---|
| 10-way 列表 | 每道关系预测题印在题目里的 10 个候选关系（1 个正确答案 + 9 个干扰项） |
| 负样本 / 负关系 | 故意拿来当「错误答案」的关系，用来训练或打分 |
| uniform | 按字典序随便抽的负关系，作为「没有结构信息」的对照 |
| tail_range | 尾实体集合与正确答案重叠的负关系，原先指望「类型易混淆」 |
| path_local | 出现在问句头实体附近 2 跳内的负关系，原先指望「图邻域易混淆」 |
| listed | 题目 10-way 列表里那 9 个干扰项 |
| 官方 10-way | 论文 `process.py --seed 2026` 给 val/test 抽的 10 个候选；本次评测用的就是这一套 |
| 训练 listed 负样本 | 7B Stage 2 训练时现抽的 9 个负关系；**不印进题面**，也不等于官方 10-way |
| surface | 字符串长得像正确答案的近形关系 |
| adapter | 写入当前图知识的 LoRA 参数；关掉 adapter = 只用底模 |
| 生成 EM | 模型自由生成答案后，字符串是否与标准答案完全一致 |
| Hits@1 | 续写打分时，正确答案是否排在所有候选的第一名 |
| 闭集 EM | 同一题目前缀下，对官方 10 个选项打续写分，取 argmax；与自由生成 EM 分开报 |
| smoke | 小规模评测切片：验证 32 题 / 测试 64 题（0.5B 也只用 64 道训练 QA） |
| pilot | 更大规模评测切片：验证 128 / 测试 512。0.5B 还没按这个规模训；7B 是拿已有 adapter 在该切片上解码 |
| full | 官方全量 val+test：验证 4951 + 测试 4944 = 9895 题 |
| B1 | 配方对齐的原版 GRIP：只优化生成 loss，不加对比 loss。7B 负样本不进 B1 的题面、也不进 B1 的损失。不是一字不差的官方复现 |
| listed 对比 | 生成 loss + 对候选干扰项做 InfoNCE。负样本只在这一步给 listed 打分；0.5B 用训练题自己的 10-way；7B 实验 F/G 从训练 QA 关系词表（370 种）抽 9 个；当前默认改为从官方训练图关系（198 种）按 `process.py` 抽 |
| H1–H5 | 实验方案里的五条假设，见第 1 节 |

硬度怎么比：负关系的续写分数越高、正确答案与负关系的分差（margin）越小、Hits@1 越低，说明该负关系越容易把模型搞混。

## 0. 一句话结论

按图结构造出来的负关系（`tail_range`、`path_local`）几乎不是模型真正会选错的那些答案，因此不宜拿来当训练主信号。主信号应对准模型实际在选的决策集合：题目 10-way 里的干扰项，以及一部分近形 / OOV 错误。

**Qwen2.5-7B 在官方 NELL23K 全量 val/test（9895 题）上，listed 对比同时超过原版 GRIP：**

| 协议 | B1 | listed | listed − B1 |
|---|---:|---:|---:|
| 自由生成 EM（测试 4944） | 84.91% | **89.12%** | **+4.21 pp** |
| 自由生成 EM（全量 9895） | 85.02% | **88.82%** | **+3.80 pp** |
| 10-way 闭集 EM（测试） | 86.93% | **92.05%** | **+5.12 pp** |
| 10-way 闭集 EM（全量） | 86.90% | **91.71%** | **+4.81 pp** |

论文 Table 3 的 GRIP-Qwen-7B NELL23K 参考 EM 是 87.74%。这次 B1 自由生成 85.02%，略低；listed 自由生成 88.82%，已超过该参考分。B1 和论文同路（Stage 1 背图、Stage 2 只做生成、训练题不印 10-way），但只是配方对齐：任务 JSON 是本地按 `seed=2026` 生成的，训练走 RecurrentGRIP 包装，EM 是硬匹配。不要把这 2.7 个百分点说成「B1 多吃了负样本」。主对比永远是同一份 Stage 1 上的 listed vs B1。论文门槛「listed 闭集 > B1 自由生成、且看官方测试集」也过了（92.05% vs 84.91%）。

0.5B、64 题 smoke 仍然是反例：对比把列表内选错从 26 压到 1，但列表外生成从 21 涨到 53，整体 EM 从 51.0% 掉到 43.8%。7B 全量上这个代价还在（OOV 322→425），但被列表内收益盖过（1160→681）。不要把 64 题掉点写成论文阴性，也不要把 listed 说成新的结构负采样理论：本质是同一份图 LoRA 上多加了一条候选排序损失。不要开 `path_local` / `tail_range` 的 B2–B10。

同源替换（实验 H）目前只有 96 题：198 listed 88.54% vs 同一份冻结 B1 86.46%（+2.08 pp），test 64 题打平，涨点全在 val。列表内错误压得比 370 listed 更狠（10→4 vs 7），OOV 更差（3→7）。这还不能改写上面的全量数字。

**数据来源一句话**：7B 的 Stage 2 用的就是论文那套生成 QA（12,014 条 = 8,000 context QA + 4,014 reasoning QA，由论文脚本按 `seed=2026` 生成）；评测的 10-way 按论文 `process.py`、`seed=2026` 复现，不是另造一套；实验 F/G 的训练 listed 负样本是从 370 个 QA 关系词表里抽的。实验 H 已改成从官方 198 个训练图关系、按同一套 `process.py` 规则抽，既不印进题面，也不等于把 val/test 的 10-way 抄进训练。H 的 smoke 仍高于冻结 B1，但弱于 370 listed，更大切片还没解。细节见 §3.3、§4.8。

## 1. 研究问题与定位

**要回答的问题**：GRIP 把图写进 LoRA、推理时不再把图喂给模型。在这个设定下，加上候选级对比，能不能让模型更好地区分正确答案和易混关系，同时不把原来的生成质量打坏？结构感知负关系是最初设想的对比来源，已被证伪；当前主信号是决策集合上的 listed 对比。

**工作标题**：Contrastive In-Parameter Graph Reasoning with Structure-Aware Hard Negatives。这是工作名，不是已经成立的创新声明。

**文献结论**（`RESEARCH_REVIEW.md`，2026-09-02）：几个组件分开看都不新，新意只在组合。

| 组件 | 最近先例 | 本项目怎么用 |
|---|---|---|
| 结构负样本 | SANS（在 k 跳邻域里抽负实体） | 改成抽负关系，并接到大模型关系预测 |
| 对比 loss | SimKGC 的 InfoNCE | 保留 GRIP 的图 adapter，不改表示学习骨架 |
| 生成式硬负样本 | ACL 2023 Findings | 第一版不用第二个生成器，只用图上的确定性规则 |
| 图写入参数 | GRIP（KDD 2026 / arXiv:2511.07457） | 原版 GRIP 只优化生成 likelihood，没有候选级排序 loss |

投稿定位按设计时判断是 **analysis + extension**（workshop / findings / 短文），不是主会长文。机制假设 H4（「图知识由 adapter 承载」）需要多张图之间打乱 adapter 做对照；NELL23K 只有一张图，做不了完整的机制声明。

五条假设：

- **H1**（方法）：加上对比训练之后，候选排序的 MRR / Hits@1 提高，且生成 EM 不明显下降。
- **H2**（前提）：`tail_range`、`path_local` 这类结构负关系，比 uniform 更难。
- **H3**：三个负关系家族合用，比只用其中一个更好。
- **H4**（机制）：正确图 adapter 相对「关掉 adapter / 打乱 adapter」的分数优势变大。
- **H5**：观察到的收益不是因为多算了几步、或多看了几条样本。

依赖关系：结构版 H2 不成立，就没有理由用 `path_local` / `tail_range` 去做 H1。listed 的卫生检查通过后，H1 改为「listed 对比 vs 原版 GRIP」。7B 全量上 H1 已过门；H5 未做，所以还不能把涨点说成纯损失设计。H4 仍然需要多图，NELL23K 做不完。

### 3.3 模型训练全流程（汇报用这一页）

这一节只讲「怎么训、数据怎么走」，不讲实验结果。0.5B / 7B 数字见第 4 节。

核心就一件事：**底模和 LoRA 结构不变，训练题也不另造一批。先把图写进同一份 adapter，再分叉：B1 只练生成，listed 多加一条候选排序损失。** 不是数据增强（样本数不变），也不是 RecurrentGRIP 那种把同一层循环 K 次。

```text
底模 Qwen2.5（0.5B 或 7B-Instruct）  ← 本地 model_cache，不从头训整网
        │
        ▼
加上图专用 MLP LoRA（r=4 / α=8，全部 down_proj / up_proj / gate_proj）
        │
        ▼
Stage 1（两条臂共用，--stage s1）
  只做生成 loss，把训练图写入 LoRA；不看 10-way，没有 InfoNCE
        │
        │   存成 $RUN_DIR/s1_adapter
        ▼
Stage 2 从同一份 s1_adapter 各复制一份，QA epoch 对齐（默认 10 轮，不停）
        │
        ├─ B1      --stage b1      L = L_生成                 λ = 0
        └─ listed  --stage listed  L = L_生成 + λ L_InfoNCE   λ = 1.0
        │
        ▼
评测（闭卷）：prompt 里不再给原图，只用官方对齐的关系预测题
        ├─ 训练脚本内：smoke / pilot 切片上的自由生成 EM
        └─ 另开解码：configs/run_full_decode_eval.sh
              自由生成 EM（主指标）+ 官方 10-way 闭集 Hits@1 / MRR
```

入口：`scripts/train_listed_contrastive.py`。一键脚本：0.5B 用 `configs/run_listed_vs_b1.sh`，7B 用 `configs/run_listed_vs_b1_qwen7b.sh`。`--stage` 可以是 `s1` / `b1` / `listed` / `all` / `compare`。一张 GPU 跑 `all`（先 Stage 1 再两条 Stage 2）；两张 GPU 可在 Stage 1 之后并行 fork B1 / listed。

#### 第 0 步：数据各管各的，训练看不见测试题

NELL23K 被拆成三种角色，不能混用。

| 数据 | 角色 | 训练用不用 |
|---|---|---|
| `train.txt`（约 2.4 万条边，2.1 万实体，198 种关系） | 图本身；Stage 1 要背的内容 | 用 |
| 训练 QA | Stage 2 要做的问答题 | 用 |
| `valid.txt` / `test.txt` | 只当考题 | **训练不用**，只评测 |

验证/测试会改写成官方 10-way（`process.py`，`seed=2026`）。这只改考卷，不改训练集。官方本来就不给训练题抽 10-way。

0.5B 和 7B 的 Stage 2 输入不同，评测文件相同：

| | 0.5B smoke | 7B（当前主实验） |
|---|---|---|
| Stage 1 | 从图边生成 context 文本（约 4.5 万条） | `grip_nell23k_tasks.json` 里 80,820 条 context + summarization |
| Stage 2 QA | 对齐文件里 `split==train` 的 64 道关系预测 | 同一任务文件里 12,014 条生成 QA |
| listed 负样本 | 该训练题自己印的 9 个干扰项 | 题面通常没有 10-way；**关系类**题目从训练 QA 关系词表抽 9 个（`k=9`，种子 `2026+index`）；非关系题不打 InfoNCE |
| 评测 | 对齐后的 val/test | 同样是对齐后的 val/test（smoke 96 / pilot 640 / 全量 9895） |

`build_qa_assets()` 里 `split != "train"` 直接跳过。7B 也不读官方测试 10-way。因此 listed 不是把考题选项提前塞进训练。

题面在评测时印着 10 个选项，B1 和 listed **两边都看见**。这是 GRIP 原协议，不是 listed 多出来的信息。listed 多的只是：训练时用训练负样本算 InfoNCE。

7B 实验 F/G 有一个需要写进论文的限制：训练负样本是 370 词表随机抽的，测试才是官方 10-way。这不是泄露，而是训练/测试选项不同源。实验 H 只换 InfoNCE 输入、不改损失，用来拆掉这个质疑。

#### 10-way 选项与 listed 负样本从哪来（三处来源，不要混）

题目本身的头实体、尾实体、金关系都取自 NELL23K 划分，不是手写新题。有争议的只是「那 9 个干扰项」。三处用法各抽各的：

| 用在哪 | 9 个干扰项从哪来 | 随机数 | 是否印在题面 | 代码 |
|---|---|---|---|---|
| 评测（smoke / pilot / 全量 val+test） | 论文官方协议：从**训练图关系词表**（198 种）抽 9 个 | `numpy.random`，全局 `seed=2026` | 印 | `official_lists.py` 复现 `data/raw_datasets/nell23k/process.py` |
| 7B Stage 2 训练（listed 臂，实验 F/G） | 从**训练 QA 金答案关系词表**（370 种）抽 9 个 | Python `random.Random(2026 + 题目下标)` | **不印** | `task_file.py: sample_listed_negatives()` |
| 7B Stage 2 训练（listed 臂，实验 H） | 从**训练图关系词表**（198 种）抽 9 个，规则与评测相同 | 私有 `numpy.random.RandomState(2026)`，按训练 QA 顺序消耗；不读 val/test 三元组 | **不印** | `task_file.py` + `official_lists.py` |
| 0.5B smoke Stage 2 训练 | RecurrentGRIP 给训练题自己抽的列表 | 按划分分开的随机流 | 印 | RecurrentGRIP `prepare_recurrent_nell23k.py` |

官方本来就不给训练题抽 10-way，所以 7B 和 0.5B 的训练选项都是自造的；只有评测那一行是论文原协议。RecurrentGRIP 自己抽的评测列表与官方几乎对不上（96 题里 0 题相同，见 §4.3），所以评测统一改写成官方那一套。

**7B 那 9 个负样本的判定规则**（`task_file.py`，已在 12,014 条 QA 上实跑）：

1. 逐条训练 QA，取最后一个 `<answer>...</answer>` 当金答案。
2. 只有「关系类」金答案进词表：不是 `yes`/`no`；或以 `concept:` 开头；或题干含 `relation between` 且答案是单个无空格词、又不是 `concept_` 实体名。实体题（金答案以 `concept_` 开头，共 5,439 条）、摘要题、普通事实题都不进。
3. 结果是一份 **370 个关系**的词表。
4. 只有关系类题才抽负样本：词表去掉当前金关系后 `random.sample(pool, 9)`；词表不足 9 个就全用。非关系题 `listed_relations` 为空，这一步 InfoNCE 为 0。
5. 这 9 个只用在同一前缀下给正负候选打续写分，**不改题面**，也不做近形 / 结构筛选。

**实测规模**（这次 7B 训练真正吃进去的量）：

| 项 | 数量 |
|---|---|
| `context_samples`（Stage 1） | 80,820 = 44,820 context + 36,000 summarization |
| `qa_samples`（Stage 2） | 12,014 = 8,000 context_qa + 4,014 reasoning_qa |
| 其中关系类、带 9 个负样本 | **3,297 / 12,014** |
| QA 金答案关系词表 | 370 种 |
| 每条关系题的候选 | 1 正 + 9 负 = 10 |
| 每 epoch 被打分的候选续写 | 3,297 × 10 = 32,970 |
| 10 个 epoch 合计 | 32,970 × 10 = **329,700** |

最后一行就是 §3.3 和第 4 节里那个 329,700 的来历。注意它是**被打分的候选续写条数**，不是 forward 次数：同一题的 10 条续写打包成一次 forward（`score_candidate_rows` 把 rows 拼成一个 batch），所以 listed 相对 B1 多出来的 packed forward 约 3,297 × 10 = 32,970 次。H5 要按 forward 次数论证算力，不能直接把 329,700 当算力。

**实验 H 的替换规则**（代码已切默认；smoke 已出，更大切片解码排队中）：

1. 词表改成 `train.txt` 按 `process.py` 插入序得到的 **198** 个训练图关系，全部是 `concept:` 形式。
2. 抽样规则与评测相同：拷贝词表、去掉金关系、`numpy.random.permutation` 取 9 个，再把金关系加回去打乱（只为消耗同一条随机流；题面仍不印选项）。
3. 随机数是私有 `RandomState(2026)`，按训练 QA 顺序消耗。不用评测那条全局 `np.random.seed(2026)`，也不读 `valid.txt` / `test.txt`。
4. 金答案若是裸名（如 `worksfor`），对齐到 `concept:worksfor` 后再排除；InfoNCE 的正样本续写仍是题里原来的金答案字符串。
5. 对不上 198 词表的关系类题不打 InfoNCE。实测：3,297 条关系题里 2,656 精确匹配、597 别名匹配、**44 条对不上**。因此实验 H 大约是 3,253 条题 × 10 候选。
6. `--listed_negative_source qa_vocab` 可原样复现实验 F/G。

任务文件 `grip_nell23k_tasks.json`（85 MB）是生成产物，没有进 git；它由论文脚本按 `--num-context-qa 8000 --num-reason-qa 2000 --num-summarization 6000 --seed 2026` 生成（`scripts/01_generate_nell23k_tasks.sh`）。

#### 第 1 步：加载底模，加上图专用 LoRA

- 模型从 RecurrentGRIP 快照的本地 `model_cache` 读：`Qwen2.5-0.5B` 或 `Qwen2.5-7B-Instruct`。
- LoRA 打在全部 MLP：`down_proj` / `up_proj` / `gate_proj`。这份 LoRA 就是后来推理要加载的图 adapter。底模冻结，只更新 adapter。
- 随机种子 2026。

推理时 prompt **不再出现原图**。图知识被认为写在 adapter 里。这是 GRIP 的设定，也是知识图谱补全里常见的直推设定：实体多半在训练图里见过，测试缺的是边。

#### 第 2 步：Stage 1，把图写入参数

目标不是做 10 选 1，而是让 adapter 记住训练图。只有语言模型生成 loss，没有 InfoNCE，也不看 10-way。

- 0.5B：`GenGraphContextTask` 把图的三元组读成 context 文本再生成。
- 7B：直接用任务文件里已经生成好的背图 + 摘要文本。

B1 和 listed **完全共用**这一步。训完存 `s1_adapter`。后面两条臂都从这份权重接着训，图知识起点一样。7B 这次 Stage 1 约 3.8 小时。

#### 第 3 步：Stage 2 分叉，只在这里出现对比

从同一份 `s1_adapter` 复制出两条，各自再训 10 个 QA epoch。不做提前停止，让生成目标的训练步数对齐（H5 仍未对齐前向次数）。

题目前缀做到 `<answer>` 为止，例如：

```text
[system] ...
[user] Given the context graph titled nell23k, ...
       爱沙尼亚 和 欧洲 之间是什么关系？请从下面 10 个里选：…
[assistant] <answer>
```

**负样本怎么作用 listed（人话）**：题面不改。同一句问完之后，listed 额外问模型：接着写正确答案有多顺、接着写那 9 个错误关系有多顺。InfoNCE 要求正确答案的分在这 10 个里最高，否则就回传梯度。B1 的 \(\lambda=0\)，这一步整段跳过，那 9 个关系等于不存在。所以负样本不是新训练题，只是 listed 那条排序损失的计算器输入。

**一步 `compute_loss` 实际做了什么：**

1. 对整段 chat QA 算原来的生成 loss（B1 和 listed 都有）：模型要续写出正确答案。
2. listed 额外：同一前缀下，把「正确答案 + 最多 9 个干扰项」拼成若干条 continuation，一次 packed forward，得到**长度归一化**续写 log-likelihood \(s_+\)、\(s_1,\ldots,s_K\)。
3. InfoNCE 就是把这些分数当 logits、正确答案当第 0 类的交叉熵（`candidate_infonce_loss`，τ = 1.0）：

```text
L_InfoNCE = -log  softmax(s / τ)_正样本
L_B1      = L_生成
L_listed  = L_生成 + λ L_InfoNCE     （当前 λ = 1.0）
```

数据集仍是 **一道题一条样本**。9 个干扰项只作为附加字段进 `ListedContrastiveTrainer`，不另开 9 条训练文本。所以这是加损失调同一份 LoRA，不是负样本数据增强。非关系题（7B 任务文件里的 yes/no、摘要题等）没有 listed 字段，这一步 InfoNCE 为 0。

打分时用 `unwrap_model`，避开 Accelerate 把 logits 转 fp32 导致的 OOM。listed 因此常用 `batch=1`。

7B 实际开销：B1 约 3.7 小时，候选评分为 0；listed 约 13.5 小时，共给 329,700 条候选续写打过分。12,014 条 QA 里只有 3,297 条是关系题，剩下 8,717 条（yes/no、摘要、实体题等）不额外打分；同一题的 10 条续写打包成一次 forward，所以多出来的 forward 约 32,970 次。算法见 §3.3「10-way 选项与 listed 负样本从哪来」。

#### 第 4 步：评测，闭卷

加载各自的 Stage 2 adapter。题目是官方对齐后的关系预测。两种协议都报，且必须分开：

1. **自由生成 EM**（主指标 / 方法门禁）：greedy 解码，字符串是否和标准答案完全一致。训练脚本在 smoke / pilot 切片上当场报。
2. **闭集打分**：同一前缀给官方 10 个选项打续写分，看金答案是不是第 1。全量 9895 题不重训，另跑 `configs/run_full_decode_eval.sh`（约 5.3 小时）。

闭集用测试题的 10-way，这是评分方式，不是训练。两边用同一套考卷。

#### 产物目录

```text
$RUN_DIR/
  environment.txt          机器、超参、输入文件
  s1_adapter/              共享的图 LoRA
  b1/adapter/              原版 GRIP
  b1/summary.json          切片生成 EM

  listed/summary.json

```

全量解码另开目录，例如 `results/runs/20260915_140500_qwen7b_full_decode/`，里面是 `b1/`、`listed/` 和 `comparison_closed_set.json`。

#### 怎么跑

```bash

```

#### 和「多迭代 / 加数据」差在哪

| | 普通多 epoch | RecurrentGRIP 循环 K 步 | listed 对比 |
|---|---|---|---|
| 改什么 | 同一条生成 loss 再看几遍 | 推理时同一层再跑几遍 | Stage 2 的训练目标 |
| 每一步看什么 | `(题目, 正确答案)` | 同一题的隐状态 | 同一前缀的 10 个候选续写 |
| 样本数 | 可增多 | 不变 | **不变** |
| 推理 | 一次生成 | 必须跑 K 次 | 仍可一次 greedy，或对 10-way 打分 |

#### 流程上不是泄露，但仍有三件事要诚实写

1. 测试 10-way 只出现在评测题面和闭集打分，不进入 Stage 2 的 InfoNCE。
2. 7B 训练 listed 与测试 listed 不是同一套选项。
3. listed 每步更贵。epoch 对齐了，算力没有对齐；这是 H5，不是泄露问题。

## 4. 实验过程与结果

### 4.1 实验 A：候选审计（不训练，只检查数据能不能用）

**做法**：在 smoke 的 160 道题（训练 64 / 验证 32 / 测试 64）上，为每道题生成各类负关系；过滤训练、验证、测试里出现过的全部三元组；检查有没有漏网的已知事实，以及每个家族有没有抽到东西。

**对齐官方列表之前**（仍用 RecurrentGRIP 自己抽的 10-way），结果在 `results_nell23k_audit.json`：

| 负关系家族 | 抽到的条数 | 泄漏已知事实 |
|---|---|---|
| uniform | 640 | 0 |
| tail_range | 485 | 0 |
| path_local | 523 | 0 |
| random | 640 | 0 |

三个结构/对照家族都有候选，过滤也通过。这一步只说明「能造出合法的负三元组」，**不说明这些负关系更难，也不说明它们等于模型会生成的错答**。

**对齐官方列表之后**，结果在 `results_nell23k_audit_aligned.json`：listed 1440 条（每题正好 9 个干扰项）、surface 601 条、hallucinated 640 条，泄漏仍为 0。

---

### 4.2 实验 B：H2 零训练硬度门禁（不训练，只给已有模型打分）

**问的是**：模型觉得哪一类负关系更难？

#### B.1 第一次打分（2026-09-03）——实验不干净，不能当证伪依据

当时加载的是失败的 attention-LoRA pilot adapter：开 adapter 的生成 EM 只有 **4.5%**，关掉 adapter 反而有 **22.7%**。打分用的题目前缀也没有套 GRIP 的 `"Given the context graph titled ..."` 模板。

那一次的数字：`tail_range` 有 50.7% 的题目比 uniform 更难，`path_local` 只有 42.5%。表面上看像「结构负关系并不更难」。但这次实验不干净——adapter 自己在拖后腿，不能用来否证负关系的设计。

后来 RecurrentGRIP 的 `quick01_storage_quick`（MLP LoRA 打在全部 MLP 层）把这个前提翻过来了：

```
开正确 adapter：生成 EM 47.8%
关掉 adapter：  生成 EM 22.5%
```

在当前环境里，「图已经写进 LoRA」这件事成立。因此：H4 不再被那条失败的 attention-LoRA 基线直接否掉；H2 必须换到这份能存图的 adapter 上重测。

#### B.2 换 MLP storage adapter 重测（2026-09-09）

- 加载的 adapter：`quick01_storage_quick/adapter`
- 对 160 道题的每一个候选关系，算归一化续写分数
- 两组对照：开正确 adapter（`--control correct`）vs 关掉 adapter 只用底模（`--control none`）

| 负关系家族 | 开 adapter 时负关系均分 | 开 adapter 时 margin | 开 adapter 时 Hits@1 | 关 adapter 时负关系均分 | 关 adapter 时 margin |
|---|---|---|---|---|---|
| uniform | -1.658 | 1.373 | 94.4% | -4.588 | 3.777 |
| tail_range | -1.625 | 1.330 | 92.1% | -4.573 | 3.727 |
| path_local | -1.727 | 1.453 | 92.5% | -4.708 | 3.899 |
| random | -1.990 | 1.706 | 94.4% | -5.164 | 4.353 |

逐题配对：该家族是否比同一题上的 uniform 更难？

| 模型条件 | tail_range 比 uniform 更难 | path_local 比 uniform 更难 |
|---|---|---|
| 开正确 adapter | **59.9%**（91/152） | **43.2%**（63/146） |
| 关掉 adapter（底模） | **47.4%**（72/152） | **43.8%**（64/146） |

开 adapter 时，`tail_range` 按划分切：训练集 60.3%、验证集 59.4%、测试集 59.7%。全部题目合计 z=2.43，p≈0.015；**只看测试集** 37/62，z=1.52，p≈0.13。`path_local` 在训练、验证、测试上全都低于 50%。

**判读**：

1. **`path_local` 明确失败。** 开 adapter 和关 adapter 都觉得 `path_local` 比 uniform 更容易。不要再把 `path_local` 当硬负关系。
2. **`tail_range` 方向对、幅度弱。** 相对底模的 47.4%，开 adapter 后抬到 59.9%，三个划分方向一致；但测试集单独不显著，Hits@1 只从 94.4% 掉到 92.1%。这个幅度不够支撑「开 B2–B10 训练」。
3. **这份 MLP adapter 确实把图写进去了。** 正确答案的续写分数从关 adapter 的 -0.811 升到 -0.285。9 月 3 日那次「开 adapter 判别力更差」的观察，不再适用于当前 adapter。
4. **绝对 Hits@1 虚高。** 题目文本里已经印了 10 个选项；审计脚本另外造出来的负关系，不一定出现在这 10 个里。家族之间谁比谁难，这个相对比较仍可用；绝对 Hits@1 不能当成训练后 EM 会涨的预期。

9 月 3 日旧结论里有一句「底模也证伪，所以负关系设计本身不成立」。这句话不成立：底模看不见图结构，不能用来否证结构负关系。真正能干净否证的只有 `path_local`；`tail_range` 仍是未决的弱信号。

### 4.3 实验 C：对齐官方 10-way，并检查负关系能否打中真实错答

**发现的协议问题**：官方 GRIP 用 `process_raw_data.py --datasets nell23k --seed 2026`，只给验证集和测试集抽 10-way 列表。RecurrentGRIP 用另一套按划分分开的随机数。同一道 `question_id` 上，两套 10-way 几乎完全不同。

| 题目集合 | 验证+测试题数 | 与官方 10-way 完全相同的题数 | 平均 Jaccard |
|---|---|---|---|
| smoke | 96 | **0** | 0.081 |
| pilot | 640 | **0** | 0.074 |

对齐后的题目写在 `data/nell23k/recurrent_relation_prediction.aligned.json`（pilot 另有一份 `_pilot`）。训练集官方本来就没有 10-way，训练题继续用 RecurrentGRIP 抽的列表。

**更关键的发现：按图结构造的负关系，几乎不是模型会生成的错答。**

对照对象：`quick01_storage_quick` 在 640 道验证+测试题上的自由生成（开正确 adapter，EM 47.8%）。334 道错题分成三类：

| 错误类型 | 数量 | 含义 |
|---|---|---|
| 列表内误选 | 174 | 模型输出了 10-way 里的某个干扰项 |
| 词表内、列表外 | 70 | 模型输出了知识图谱里真实存在的关系，但这个关系不在当前这 10 个选项里 |
| 真 OOV | 90 | 模型造了词表里没有的字符串（常见是前缀拼错，例如少写、多写几个字母） |

各家族负关系，有多少次正好等于模型这次的错答：

| 负关系家族 | 打中列表内误选 174 | 打中词表内列表外 70 | 打中真 OOV 90 |
|---|---|---|---|
| 模型当时看到的那份 10-way / `listed` | **174/174** | 0/70 | 0/90 |
| 官方 10-way（拿去套已经跑完的 quick01） | 9/174 | 8/70 | 0/90 |
| surface（近形关系） | 14/174 | **17/70** | 0/90 |
| hallucinated（事先拼出来的幻觉字符串） | 0 | 0 | **0/90** |
| tail_range | 11/174 | 7/70 | 0/90 |
| path_local | 12/174 | 18/70 | 0/90 |
| uniform / random | 0 | 0 | 0 |

审计用的 160 题里，有 96 题落在 quick01 的验证/测试里（对 37 题、错 59 题）：模型错答落在 `tail_range` 里只有 2/59，落在 `path_local` 里只有 1/59。题目上的 10-way 被这两个家族覆盖到的选项也大约只有 2%。

**因此改负关系的瞄准点**：

1. 主负关系改成 `listed_relation`：评测时模型看到的那份 10-way 里，全部 9 个干扰项。这样能覆盖约 52% 的生成错误（174/334 是列表内误选）。
2. 把 val/test 列表改写成官方协议，是为了以后训练和评测用同一套选项。这个对齐**救不了已经跑完的 quick01**：quick01 当时看到的是 RecurrentGRIP 列表，拿官方列表去套，只能打中当时 174 次列表内错误里的 9 次。
3. `surface_relation` 作为第二家族，用来覆盖「生成了真实关系、但不在 10-way 里」这类错误（17/70）。
4. 事先拼出来的幻觉字符串，一个真 OOV 都召不回（0/90）。真 OOV 是解码问题：要么生成时强制只在 10-way 里选，要么用模型自己滚出来的错答当负样本。
5. `path_local` 和 `tail_range` 不再当主硬负关系。

### 4.4 实验 D：对齐官方列表后，再测 listed 是否比 uniform 更难（仍不训练）

题目换成官方 10-way 写进 prompt 之后，再用同一份 storage adapter 打续写分。

| 负关系家族 | 开 adapter 负关系均分 | 开 adapter margin | 开 adapter Hits@1 | 关 adapter Hits@1 |
|---|---|---|---|---|
| uniform | -1.650 | 1.353 | 96.9% | 96.9% |
| **listed** | **-0.957** | **0.661** | **51.3%** | **38.1%** |
| surface | -1.878 | 1.580 | 92.4% | 93.7% |
| hallucinated | -5.245 | 4.949 | 100% | 100% |
| tail_range | -1.634 | 1.327 | 94.7% | 96.1% |
| path_local | -1.697 | 1.409 | 91.8% | 95.2% |

listed 是否比同一题的 uniform 更难：开 adapter 时 **159/160 = 99.4%**（训练 64/64、验证 31/32、测试 64/64）；关掉 adapter 时 **160/160**。

**怎么读这张表**：

1. 卫生检查通过：负关系终于落在模型要选的那 10 个选项里。listed 的 Hits@1 从 uniform 的 97% 掉到 51%，这才像「真会搞混」。
2. **listed 比 uniform 更难，不是创新。** 关掉 adapter 之后，listed 仍然 160/160 更难。难，主要是因为这 9 个干扰项印在题目上，不是因为图结构。
3. Adapter 仍有一点判别力：listed 的 Hits@1 从底模的 38% 升到 51%。后面如果对比训练有用，目标是把剩下那一半「列表内仍搞混」再压下去，并且不能把自由生成的 EM 打坏。

### 4.5 实验 E：第一次对比训练（0.5B smoke，2026-09-09）

到目前为止，真正更新过模型参数的训练只有这一次。这次训练是方法门禁，不是论文结果。

**设计**：先共用一次 Stage 1，把 NELL23K 图写进 MLP LoRA；再从同一份 Stage 1 adapter 分出两条 Stage 2。两条 Stage 2 都跑满 10 个 QA epoch，不做提前停止，让生成目标的训练步数对齐。

```
Stage 1（两条臂共用）  把图 context 写入 MLP LoRA
        │
        ├─ B1      只优化生成 loss          = 原版 GRIP
        └─ listed  生成 loss + 对 10-way 干扰项做 InfoNCE
```

**配置**：

| 项 | 值 |
|---|---|
| 数据 | 对齐官方列表后的 smoke：训练 64 / 验证 32 / 测试 64 |
| 底模 | Qwen2.5-0.5B，本地 cache |
| LoRA | r=4，α=8，作用在 `down_proj` / `up_proj` / `gate_proj` |
| Stage 1 | 44,821 条图 context，1 个 epoch，88 步，约 9.6 分钟，训练 loss 1.285 |
| Stage 2 | 64 道 QA，10 个 epoch，学习率 1e-3；listed 的 λ_candidate=1.0，B1 的 λ_candidate=0 |
| 评测 | greedy 解码后做 exact match；同时统计错答是否落在 10-way 里 |
| GPU | RTX 3090 24GB；随机种子 2026 |
| 运行目录 | `results/runs/20260909_listed_vs_b1_smoke_listed_vs_b1_smoke` |

**训练过程中的故障**：listed 第一轮按 batch=8 给 10 个候选打续写分时，Accelerate 把 logits 转成 fp32，显存不够（OOM）。修复方式：打分时用 `unwrap_model`，避开这条 fp32 路径；listed 改为 batch=1，打开 gradient checkpointing，从同一份 Stage 1 adapter 接着训。B1 在 OOM 之前已经训完。两条臂仍然共用同一份 Stage 1。

listed 大约训了 15.5 分钟。最后一步：生成 loss 0.463，**对比 loss 0.0019**（InfoNCE 几乎被压到 0，说明「在 10-way 里把正确答案和 9 个干扰项分开」已经学会）。B1 大约 12 秒，最后一步生成 loss 0.481。

**自由生成 EM**（验证 32 题 + 测试 64 题，共 96 题）：

| 训练臂 | 验证 EM | 测试 EM | 96 题合计 EM | 错在 10-way 里 | 生成了列表外字符串 |
|---|---|---|---|---|---|
| B1 原版 GRIP | 46.9% | **53.1%** | **51.0%** | 26 | 21 |
| listed 对比 | 50.0% | 40.6% | 43.8% | **1** | **53** |
| listed 减 B1 | +3.1 个百分点 | −12.5 个百分点 | **−7.3 个百分点** | −25 | +32 |

**判读**：

1. **对比目标本身有效。** 「在 10-way 里选错」从 26 题降到 1 题，对比 loss 收敛到接近 0。
2. **代价是解码跑出 10-way。** 「生成列表外字符串」从 21 题涨到 53 题。模型学会了「不要选这 9 个干扰项」，但没有学会「答案必须是这 10 个里的某一个」。quick01 里大约一半错误本来就是 OOV，对比 loss 覆盖不到这些错误，还可能把概率质量推到 10-way 外面。
3. **H1 在这次 smoke 上没有过门。** 生成 EM 掉了 7.3 个百分点，超过实验方案里「EM 掉幅不超过 2 个百分点」的门槛。
4. **不能外推，也不能写成论文阴性结论。** 训练只有 64 道 QA；验证集微涨、测试集大跌，方向还不稳。当时只能说：在 0.5B、λ_candidate=1、生成时不限制候选集合的条件下，listed 对比会牺牲自由生成。后面 7B 全量评测把这条「生成必跌」的判断翻过来了，见 4.6 / 4.7。

## 7. 汇报时建议怎么讲

1. **问题**：GRIP 把图写入 LoRA 之后，关系预测仍会在 10-way 里选错，或生成列表外字符串。原版只优化「生成正确答案」，没有候选级区分。训练流程见 §3.3：共享 Stage 1 存图，Stage 2 再分叉。
2. **先证伪、再转向**：图结构负关系既不是模型觉得更难的，也几乎不是它会生成的错答。模型真正在选的是题面上的选项。
3. **方法很薄，但 7B 全量有效**：同一份 Stage 1 图 adapter，Stage 2 加 InfoNCE。官方测试生成 EM 84.91%→89.12%，闭集 86.93%→92.05%。0.5B 小样本上曾把错误推到列表外、总分下跌，所以不能只报 7B。
4. **不要夸大**：这不是新的负采样理论，也不是数据增强（题量没变）。listed 比 uniform 更难只说明协议卫生。实验 G 的训练负样本（370 词表）和测试 10-way 还不是同一套；实验 H 已在同源 198 词表上重训 listed，但目前只有 96 题 smoke，而且净增益弱于 G、test 打平。B1 是配方对齐的原版 GRIP，不是一字不差官方复现；不要用 B1 对论文的 2.7 个百分点讲故事。
5. **定位**：analysis + extension。C 会 / Findings 可以按这个写。冲 A/B 需要把贡献改成「图写入参数后模型到底在和谁混淆」，并补算力对照、第二数据集或 adapter 机制实验。

   闭集解码，或训练时加「留在 10-way 内」。用来回答 0.5B 失败模式在 7B 上是否只是被规模盖过。
5. **第二张图，或 CLEGR 上的 adapter 对比**  
   前者支撑分析文跨数据集；后者才是和「任意 QA 加 loss」真正切开的机制声明。

**不建议**：再拿 `path_local` / `tail_range` 去训练；把 64 题 0.5B 掉点写成论文主结论；把 7B 涨点说成结构硬负样本的成功；在 H5 没做时对 A 会长文抱希望。
